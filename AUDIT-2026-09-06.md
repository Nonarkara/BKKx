### 2.2 The fabric is drawn twice — 1,168 buildings, two heights, by default

`AtlasView.tsx:692` sets `showRowhouseCandidates` to `true`, and the candidate
layers are `fill-extrusion` at `SHOPHOUSE_CANDIDATE_HEIGHT` (`:128`, 3.5 m +
3 m per floor from Overture `num_floors`, else 6.5 m). The OSM detail layer is
also on by default and also extrudes. `scripts/audit-hero-occlusion.py`, table B:

```
candidates whose centroid lies inside an OSM detail box:  1,168
   same height as the box                                       0
   candidate taller than the box                              139
   box taller than the candidate                            1,029
   median |difference|                                      2.5 m
```

So 1,168 of the 2,433 are rendered as two overlapping boxes of different
heights — never the same height, because one is a rounded OSM tag and the
other a statutory storey formula. `docs/audit-2026-09-06/tanao-fabric-double.png`
against `tanao-detail-only.png` (same camera, Tanao Road rows) shows it as a
lighter box poking out of, or sunk into, every amber one. The legend has no
row for the lighter box (§2.3), so a reader has no way to learn that the
stepped rooflines are two datasets disagreeing rather than a survey.

**Fix (small, on the branch):** compute `has_detail_box` at build time —
the centroid test above, one boolean per candidate, written into the
candidates geojson by its exporter — and filter the extrusion layers on it,
so a candidate only extrudes where no OSM footprint already does. Keep the
outline layer for all 2,433. Alternatively default the candidates off and
leave the extrusion behind the toggle; but the flag is the honest version,
because it says per building which representation won and why.

### 2.5 The committed hero geojson is one environment's last digit

Running `site/scripts/build-hero-monuments.py` in the worktree changed
`bkk-hero-monuments.geojson` by two bytes: the rings of
`wat-arun-satellite-3-spire` and `wat-pho-srisuriyothai-finial` differ from the
commit by 1 × 10⁻⁷ degrees in one coordinate each. Three local runs agree with
each other, so the generator is deterministic; the committed file was produced
on a different platform's last digit. `dataset-manifest.json`'s checksum for
the file follows it. Harmless geometrically; it means `git status` is dirty
after every build and any future staleness guard on this file would flap.

**Fix, as first written:** round to six decimals, as the register does.
**Withdrawn in the disposition below** — six decimals move a sub-metre
finial's vertices by a tenth of its size and change the rasterised block
plan. Three runs here agree byte for byte, so the digit is a stale commit,
not arithmetic, and the fix for that class is a CI step that fails when a
build modifies any committed generated file (`d7572bd`).

Wat Arun renders correctly because nothing was ever drawn under it. Every
other monument the "hero" work built — 44 of the 67 parts on this branch, 61
of 88 on the fabric branch, stand inside a box, and with the Golden Mount's
three that is 64 parts entirely below a box top — has been invisible
since the layer shipped, and the fabric branch's 21 new parts (Loha Prasat,
the prasats) went straight into the same boxes. This is the repository's moat
feature — "temples that should look distinctive from other boxy buildings" —
rendering as boxy buildings.

Why nobody saw it: the shipped page cannot be screenshotted from a sandbox
that cannot reach the tile server, and the tests for the hero layer check

feature whose centroid falls inside the hero's lowest part (or whose polygon
contains the hero's centroid — both directions, as the script does), and write
which hero hid it (`hidden_by`). Then `audit-hero-occlusion.py` becomes
`verify-hero-occlusion`: it fails the build if any part is entirely below a
visible box. The applier already does the block-world equivalent (clears the
hero's columns first); the atlas needs the same rule.

## 4. My own work, audited to the same standard

### 4.1 Every block plan puts the ground 126 blocks in the sky

`scripts/build-hero-monument-blocks.py:59` — `DEFAULT_GROUND_Y = 64`, "Minecraft
sea level", with a comment that this is "the same ground frame" as the moat
surface (y = 63) and gate markers (y = 64) in `apply-rattanakosin-to-world.py`.
`scripts/build-shophouse-blocks.py` (mine) and `scripts/build-shophouse-fabric.py:68`
(Cursor's) copy the constant. All three committed plans say `"groundY": 64`.

The world they are for was generated by Arnis 3.0.0 with `terrain_elevation:
false` (`worlds/bangkok-historic-core-java/bkkx-manifest.json`) — a superflat.
Arnis's ground is not at sea level:

- `args.rs` in the Arnis source: `--ground-level`, `default_value_t = -62`
  (v3.1.0; the shallow clone cannot show 3.0.0's, see §8).
- `heritage-register.json` records `spawnY: -50` for this world and `-59` for
  Ratchathewi — read from each world's `level.dat` by
  `build-heritage-register.py:166`, whose docstring says, in full:
  *"These worlds are superflat, so one height is right everywhere; reading the
  real value beats assuming Minecraft's default of 64, which is ~120 blocks of
  freefall above a world whose ground sits near y = −60."*

The repository already knew. The knowledge sat in one docstring and did not
propagate to the scripts that needed it — including mine, which I wrote after
reading the rattanakosin applier's frame and not the register's. My tests
prove the projection against 105 register blocks in X and Z, and assert
nothing about Y. Two axes proven, three claimed.

What would happen: the applier clears each hero's columns from y = 64 upward
(all air), then writes the monument from y = 64 to y = 145, roughly 126
blocks above a ground near −62. The rattanakosin applier's moat would be dug
through air and its water placed at y = 63, floating. Whether that applier was
ever run against the world is not recorded in the repository. None of the
appliers has ever been run in CI, because no world file is committed — only
manifests — so nothing could have caught this except a person standing in the
world and looking up.

**Fix:** the applier must not trust a plan's `groundY`. Probe the world —
highest non-air block over a spread of columns, take the minimum, plus one —
and re-base every part by `(probed − plan.groundY)` before writing, printing
both. Plans should state Y relative to ground, not absolute. Until then,
`--ground-y -62` is the right default, with the register's docstring as its
source, and even that is a default to be probed, not trusted. This is mine to
fix; it is small, and it is the next thing I do.

## 6. "God's Mode" — what exists, what does not, what could not be checked from here

What the audit branch (and therefore the fabric branch) actually has, all of it
covered by the 09-01 review and unchanged since:

- Worker routes proxying the BMA rain gauges and the CCTV registry; Open-Meteo
  weather and air quality (keyless); Longdo and FIRMS behind env-key slots;
  the war room; the 16-source registry with licence, auth, CORS and role per
  source; ten cameras in `cctv-cameras.ts` (six located with an evidence
  line, four placeholders that share one marker and say so); HLS support for
  iTIC/Longdo streams; YouTube facades that load nothing until clicked.

What does not exist on any branch: a Traffy Fondue adapter, route, or
catalogue entry. Any "connectivity to CCTV systems" beyond what was already
audited on 09-01.

What that gap should be filled with, in this repository's own terms — each new
source is a catalogue entry (licence, auth, CORS, role, refresh), a worker
route, and **one computed number with a verifier**, or it is not a source:

- **Traffy Fondue** is the obvious next entry: BMA's citizen-report platform,
  with a bulk export that the 2022–23 dashboards were built on. Its current
  URL, licence and schema need verifying before it is catalogued — I could
  not, because egress is blocked here — and the number it should produce is a
  join, not a feed: reports per hundred screened shophouse footprints per
  cluster, on the pressure atlas, with the report categories that touch
  building condition (collapse risk, illegal modification, fire) separated
  from the rest. That is the kind of figure the cluster pages already know how
  to publish and guard.
- The iTIC cameras not yet in the registry need an on-the-ground location line
  each before they go in; the placeholder mechanism exists precisely so that
  an unlocated camera is never drawn at a guessed point.

"God's Mode" for a dashboard that refuses to invent a reading means more
verified sources, not more panels. The infrastructure for adding one honestly
is already built; what is missing is the sources, and the sources were not
added.
